## Cross-file architecture findings

- The repository is now a full standalone application rather than a simple directory frontend.
- Shared files such as global CSS, authentication/session JS, admin.js and common API endpoints have high change impact.
- The admin folder contains many thin page shells; their behaviour often lives in shared JavaScript and APIs.
- Sensitive account paths include My Hub, profile, consent, preferences and reservations and should be audited as one ownership/security chain.
- Database migrations exist, but previous source review identified runtime schema/table creation in API code; this should be consolidated into migrations.
- Deployment spans deploy.php, .github/workflows/deploy.yml and hosting configuration outside the repository, so deployment success should be verified against the actual deployed commit.

## Previously identified concrete findings

**F-01 API error disclosure:** api/auth.php can expose exception messages. Return generic production errors and log details server-side.

**F-02 Runtime schema mutation:** api/db.php can alter the user table during normal application setup. Move this to migrations.

**F-03 Runtime table creation:** api/auth.php creates authentication-related tables from the request path. Move creation to migrations.

**F-04 Export/session issue:** api/admin-import-export.php accesses activity ID data while the relevant export SELECT was observed omitting a.id. Verify session export.

**F-05 Admin regression surface:** many admin pages plus large admin.js require feature-group testing.

**F-06 CSS override debt:** styles.css is large and bold-theme.css overlays it; control specificity and load order.

**F-07 Permission matrix:** test anonymous, family, leader, organiser and admin access against protected APIs.

**F-08 Sensitive family data:** verify strict ownership, minimal responses, logging and retention for child/consent-related data.

**F-09 External integrations:** verify credentials, timeouts, rate limits and failure handling for Google/Apple, Resend, OneSignal, geocoding and school services.

**F-10 Deployment drift:** document and test the relationship between GitHub Actions, deploy.php and the hosting web root.

## How we should use this report

We can now work through the repository in a controlled order. For each file, I can open the actual source, explain exactly what it does, show what calls it, identify bugs/risks, and only then make a change if you approve. That will let us understand the app rather than blindly patching it.
